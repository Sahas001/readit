# SSH Layer

ReadIT's network layer is SSH-only. Users connect with a standard SSH client and interact with the forum through a terminal UI rendered inside the SSH PTY session.

## Authentication model

ReadIT uses **public-key-only authentication** with an open trust model:

1. The server accepts all SSH public keys — there is no allowlist or certificate authority.
2. Identity is derived from the key itself, not from the SSH username field.
3. On each connection, the server computes the SHA256 fingerprint of the client's public key.
4. The fingerprint is used to look up or create a user record in PostgreSQL.

This approach eliminates the need for passwords, registration forms, or external identity providers. Your SSH key _is_ your account.

### Fingerprint computation

The fingerprint matches the format produced by `ssh-keygen -lf`:

```go
func Fingerprint(key gossh.PublicKey) string {
    hash := sha256.Sum256(key.Marshal())
    return fmt.Sprintf("SHA256:%s", base64.RawStdEncoding.EncodeToString(hash[:]))
}
```

The resulting string (e.g., `SHA256:abcdef123...`) is stored in the `users.pubkey_sha256` column.

### Security considerations

| Concern | Mitigation |
|---|---|
| Anyone can connect | Acceptable for a public forum. Rate limiting can be added at the network level. |
| Key rotation | A user who rotates their SSH key loses access to their old account. A future "link key" flow can address this. |
| Host key trust | The server auto-generates a host key on first run at the configured `READIT_HOST_KEY_PATH`. Distribute the fingerprint out-of-band for production use. |

## Middleware chain

The Wish server applies three middleware layers in order:

```
logging.Middleware()      → Logs session connect/disconnect events
activeterm.Middleware()   → Verifies the client allocated a PTY
bubbletea.Middleware()    → Creates a tea.Program per session
```

Middleware executes from bottom to top (innermost first), so the actual order is:

1. **`logging`** — Logs the session lifecycle.
2. **`activeterm`** — Rejects non-interactive sessions (e.g., `ssh host command`).
3. **`bubbletea`** — Calls the `teaHandler` to create a `Model` and `[]tea.ProgramOption`, then starts the Bubble Tea event loop.

## Session lifecycle

```
1. Client opens TCP connection to :2222
2. SSH handshake (host key exchange)
3. Public key auth callback → always returns true
4. PTY requested → activeterm verifies
5. teaHandler called:
   a. Extract PublicKey from session
   b. Compute SHA256 fingerprint
   c. Create tui.Model with (ctx, pool, fingerprint, logger)
   d. Return (Model, [WithInput, WithOutput, WithAltScreen])
6. Bubble Tea program starts:
   a. Model.Init() → lookupUserCmd
   b. Update/View loop runs until quit or disconnect
7. Client disconnects or presses q/ctrl+c:
   a. tea.Program exits
   b. Session context cancelled
   c. Middleware logs disconnect
```

## Configuration

| Variable | Default | Description |
|---|---|---|
| `READIT_SSH_HOST` | `0.0.0.0` | Network interface to bind |
| `READIT_SSH_PORT` | `2222` | TCP port for the SSH server |
| `READIT_HOST_KEY_PATH` | `.ssh/host_key` | Path to the ED25519 host key file |

The host key is auto-generated by Wish's `keygen` package if the file doesn't exist at startup.

## Connecting

```bash
# Standard connection
ssh -p 2222 forum.domain.com

# Local development
ssh -o StrictHostKeyChecking=no -o UserKnownHostsFile=/dev/null -p 2222 localhost

# Or use the Makefile shortcut
make ssh-test
```

The `-o StrictHostKeyChecking=no` flags are for development only — the host key changes whenever you delete `.ssh/host_key`.
